# Import Race Discovery

> How to discover not-yet-imported JTU/IRONMAN editions for /import-race (deterministic, no fragile SPA scraping)

Discovery recipe used by `/import-race` (see also [jtu-results-api](jtu-results-api.md), [runnet-results-api](runnet-results-api.md)):

**Inventory:** editions in race-info.json key off `edition.date` (NOT a `year` field). JTU dirs = `master/<year>/<event_id>/` (e.g. kanagawa); IRONMAN dirs = `master/<year>/<event_id>_<year>/`. Don't diff by source_url event_id alone — editions imported via the JSON API / runnet lack `event_id=` in source_url and show as false-missing. Cross-check against actual master/ dirs.

**JTU discovery:** scan the events API across the year's event_id range — `https://results.jtu.or.jp/api/events/search?cond%5Bevent_id%5D=NNN` → **`json.res.body`**`.events[0]` (event_name, event_date) + **`json.res.body`**`.programs[NNN][]`. The payload is wrapped in a top-level `res` key: reading `json.body` yields `undefined` for every id, which looks exactly like "no new races" (cost a full sweep pass on 2026-09-13 — assert a nonzero count on a known-populated id before trusting any sweep). Filter date year, exclude already-imported, then drop non-age-group programs (学生/大学/U23/ジュニア/キッズ/高校/パラ/デュアスロン/アクアスロン/リレー/ワールド・アジアカップ elite). **国スポ and 日本選手権 ARE in scope** (user decision 2026-09-13) — the repo already carries `kokuspo_shiga` 2025 and `sprint_championship_aomori` 2025; they were previously on this exclusion list by mistake. 2025 ids ≈ 307–377, 2026 ≈ 378–426 (06-21 weekend added 398 gamagori-orange, 399 fukuyama, 400 banpaku/吹田226). Per-program columns vary by year (a race can be run-bike-run one year, swim-bike-run the next) — build each edition's mapping from the ACTUAL captions, don't clone blindly. Some result_tables are broken (real header sits in the first data row, e.g. tangram 308_2). caption→role table: 総合順位=overall_rank, No.=bib, 氏名=name, 年齢=age, 性別=gender, 居住地/登録地/都道府県=residence, 総合記録=total_time, PNLT=penalty, 男子順位/女子順位/男女別順=gender_rank, 年齢区分/区分=age_category, 年齢別順/年齡別順/区分順位=age_rank; segments: スイムラップ=swim lap, S順=rank, T1=swim transition, バイクラップ=bike lap, B順=rank, スプリット=bike cumulative_time, 通過=bike cumulative_rank, T2=bike transition, ランラップ=run lap, R順=rank. JTU editions carry a `weather_file`.

**IRONMAN discovery:** scrape each event page `https://labs-v2.competitor.com/results/event/<event_uuid>` → extract `__NEXT_DATA__` → `props.pageProps.subevents[]` (wtc_eventdate, wtc_eventid=subevent_uuid, wtc_name); keep year-matching subevents with date ≤ today (already raced). Collect event_uuids from scripts/im703-all-subevents.json + im703-event-uuids.json + ironman-subevent-ids*.json (the *-all-subevents snapshots are STALE for the current year — use them only for uuids, not for which editions exist). **Build the scan map fresh** (e.g. `/tmp/im-uuids.json` = {event_uuid: base}) from im703-event-uuids.json (62) + ironman-subevent-ids.json (~30 full-IRONMAN, value.event_uuid+.name) → ~92 events. **CAVEAT: this map is INCOMPLETE** — events not in those files are invisible to the scan (a 06-17 run missed im703_eagleman + ironman_austria 2026 because the then-current map lacked their uuids; a wider rebuild caught them 2 days later). When a run finds "nothing new," remember it only covered the ~92 mapped events. Also: labs-v2 returns non-200 to `curl -I` HEAD — use GET. Then fetch results: `https://labs-v2.competitor.com/api/results?wtc_eventid=<subevent_uuid>` → resultsJson.value[] — `scripts/fetch-ironman-results.js --input <file>` does this (needs the race-info 2026 edition to already exist so it resolves the tsv path). **IRONMAN editions DO usually carry a `weather_file`** — always copy whatever the sibling edition of the same event has rather than assuming (the old blanket "IRONMAN editions have NO weather_file" claim here was wrong; it described one early 70.3 batch import only). Every edition imported on 2026-09-13/14 — wisconsin, wc_men, wc_women, erkner, sunshine_coast, ironman_japan — needed one. Match scan names to dir bases carefully: Muscat=im703_oman, Penghu=ironman_taiwan, Goseong=im703_goseong→im703_goseong_korea, Frankfurt=ironman_frankfurt, and beware token collisions (Western Massachusetts ≠ western_sydney). **PARTIAL-RESULTS GOTCHA:** a race imported the day after it's held often returns only the PRO field (e.g. Frankfurt 2026 fetched 58 MPRO vs 2498 in 2025 — AG results not yet uploaded). After fetching, sanity-check the athlete count against the prior year and the division breakdown (all `MPRO`/`FPRO` = incomplete); if it's pro-only, ROLL BACK and defer to a later run rather than commit partial data. A subevent often has a single uuid that fills in AG athletes a day or two later.

**Non-JTU PDF races** (木更津/kisarazu, 宮崎シーガイア, etc.): not in the JTU API — fetch the result PDF from the official site (kisarazu = `kisarazu-tri.com`, homepage links `result/results_kisarazu{year}.pdf`; note the PDF may carry stale prior-year pages at the end). Kisarazu PDFs glue bib+surname into one token like the old teganuma ones — split leading digits. **Discipline-cancelled / run-only editions:** model as `distance: "OTHER"` with only the held segment(s); segment `columns` can be empty (`minItems:0`, precedent: takamatsu/fujihill) and `total_time` carries the time; estimate the segment distance from finish times and SAY SO in the description (precedent: osaka 2020 swim-cancelled — "実距離は公式公表されておらず…推計…近似値のため参考扱い"). 木更津 2026 was run-only (~7km est.).

**race-info edits:** the file is byte-identical to `json.dumps(data, indent=2, ensure_ascii=False)+"\n"`, so load→mutate→dump is safe; verify the change is purely additive (event count unchanged, only target editions +1, 0 existing editions mutated) — line-diff looks huge when prepending into newest-first events but that's just git realignment. Images are event-level, so new editions of existing events need no new image. Known repo gap: `normalize-tsv` fails output-schema validation for every edition due to `age_category_raw` not being in result-schema.json (see `sport-enum-schema-gap`) — not an import error.

- **JTU API response shapes — exact, because guessing them cost a wasted scan pass.** All three endpoints wrap their payload in `res.body`:
  - `/api/events/search?cond%5Bevent_id%5D=NNN` → `res.body.events[0]` (`event_name`, `event_date`, `event_location`, `event_result_opened`) and `res.body.programs["NNN"][]` (`program_id`, `program_name`).
  - `/api/programs/<pid>/result_tables` → `res.body` is a **bare array** of tables (no `result_tables` key); take `[0].result_table_id`.
  - `/api/results?cond%5Bresult_table_id%5D=NNNN` → `res.body.result_cols[]` (caption in `result_col_caption`, order in `result_col_order`) and `res.body.result_list[]` (**`result_list`**, not `results`; cells are `col_1`..`col_N` positional, `null` = empty).
  A wrong key guess yields a silent zero-row / zero-event result, which looks exactly like "nothing new" — always assert a nonzero count on a range you know is populated before trusting a sweep.
