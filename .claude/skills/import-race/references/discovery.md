# Import Race Discovery

> How to discover not-yet-imported JTU/IRONMAN editions for /import-race (deterministic, no fragile SPA scraping)

Discovery recipe used by `/import-race` (see also [jtu-results-api](jtu-results-api.md), [runnet-results-api](runnet-results-api.md)):

**Inventory:** editions in race-info.json key off `edition.date` (NOT a `year` field). JTU dirs = `master/<year>/<event_id>/` (e.g. kanagawa); IRONMAN dirs = `master/<year>/<event_id>_<year>/`. Don't diff by source_url event_id alone — editions imported via the JSON API / runnet lack `event_id=` in source_url and show as false-missing. Cross-check against actual master/ dirs.

**JTU discovery:** scan the events API across the year's event_id range — `https://results.jtu.or.jp/api/events/search?cond%5Bevent_id%5D=NNN` → body.events[0] (event_name, event_date) + body.programs[NNN][]. Filter date year, exclude already-imported, then drop non-age-group programs (学生/大学/U23/ジュニア/キッズ/高校/パラ/デュアスロン/アクアスロン/リレー/国スポ/日本選手権/ワールド・アジアカップ elite). 2025 ids ≈ 307–377, 2026 ≈ 378–400+ (06-21 weekend added 398 gamagori-orange, 399 fukuyama, 400 banpaku/吹田226). Per-program columns vary by year (a race can be run-bike-run one year, swim-bike-run the next) — build each edition's mapping from the ACTUAL captions, don't clone blindly. Some result_tables are broken (real header sits in the first data row, e.g. tangram 308_2). caption→role table: 総合順位=overall_rank, No.=bib, 氏名=name, 年齢=age, 性別=gender, 居住地/登録地/都道府県=residence, 総合記録=total_time, PNLT=penalty, 男子順位/女子順位/男女別順=gender_rank, 年齢区分/区分=age_category, 年齢別順/年齡別順/区分順位=age_rank; segments: スイムラップ=swim lap, S順=rank, T1=swim transition, バイクラップ=bike lap, B順=rank, スプリット=bike cumulative_time, 通過=bike cumulative_rank, T2=bike transition, ランラップ=run lap, R順=rank. JTU editions carry a `weather_file`.

**IRONMAN discovery:** scrape each event page `https://labs-v2.competitor.com/results/event/<event_uuid>` → extract `__NEXT_DATA__` → `props.pageProps.subevents[]` (wtc_eventdate, wtc_eventid=subevent_uuid, wtc_name); keep year-matching subevents with date ≤ today (already raced). Collect event_uuids from scripts/im703-all-subevents.json + im703-event-uuids.json + ironman-subevent-ids*.json (the *-all-subevents snapshots are STALE for the current year — use them only for uuids, not for which editions exist). **Build the scan map fresh** (e.g. `/tmp/im-uuids.json` = {event_uuid: base}) from im703-event-uuids.json (62) + ironman-subevent-ids.json (~30 full-IRONMAN, value.event_uuid+.name) → ~92 events. **CAVEAT: this map is INCOMPLETE** — events not in those files are invisible to the scan (a 06-17 run missed im703_eagleman + ironman_austria 2026 because the then-current map lacked their uuids; a wider rebuild caught them 2 days later). When a run finds "nothing new," remember it only covered the ~92 mapped events. Also: labs-v2 returns non-200 to `curl -I` HEAD — use GET. Then fetch results: `https://labs-v2.competitor.com/api/results?wtc_eventid=<subevent_uuid>` → resultsJson.value[] — `scripts/fetch-ironman-results.js --input <file>` does this (needs the race-info 2026 edition to already exist so it resolves the tsv path). IRONMAN editions have NO weather_file. Match scan names to dir bases carefully: Muscat=im703_oman, Penghu=ironman_taiwan, Goseong=im703_goseong→im703_goseong_korea, Frankfurt=ironman_frankfurt, and beware token collisions (Western Massachusetts ≠ western_sydney). **PARTIAL-RESULTS GOTCHA:** a race imported the day after it's held often returns only the PRO field (e.g. Frankfurt 2026 fetched 58 MPRO vs 2498 in 2025 — AG results not yet uploaded). After fetching, sanity-check the athlete count against the prior year and the division breakdown (all `MPRO`/`FPRO` = incomplete); if it's pro-only, ROLL BACK and defer to a later run rather than commit partial data. A subevent often has a single uuid that fills in AG athletes a day or two later.

**Non-JTU PDF races** (木更津/kisarazu, 宮崎シーガイア, etc.): not in the JTU API — fetch the result PDF from the official site (kisarazu = `kisarazu-tri.com`, homepage links `result/results_kisarazu{year}.pdf`; note the PDF may carry stale prior-year pages at the end). Kisarazu PDFs glue bib+surname into one token like the old teganuma ones — split leading digits. **Discipline-cancelled / run-only editions:** model as `distance: "OTHER"` with only the held segment(s); segment `columns` can be empty (`minItems:0`, precedent: takamatsu/fujihill) and `total_time` carries the time; estimate the segment distance from finish times and SAY SO in the description (precedent: osaka 2020 swim-cancelled — "実距離は公式公表されておらず…推計…近似値のため参考扱い"). 木更津 2026 was run-only (~7km est.).

**race-info edits:** the file is byte-identical to `json.dumps(data, indent=2, ensure_ascii=False)+"\n"`, so load→mutate→dump is safe; verify the change is purely additive (event count unchanged, only target editions +1, 0 existing editions mutated) — line-diff looks huge when prepending into newest-first events but that's just git realignment. Images are event-level, so new editions of existing events need no new image. Known repo gap: `normalize-tsv` fails output-schema validation for every edition due to `age_category_raw` not being in result-schema.json (see `sport-enum-schema-gap`) — not an import error.

**2026-08-03 run learnings** (last import was 2026-07-27; this run covered the ~1-week gap):
- **IRONMAN discovery — the sitemap method supersedes the batch-uuid-file method.** `https://www.ironman.com/sitemap.xml?page=1..5` yields every race slug (~169 of them); `/races/<slug>/results` embeds the labs-v2 `/results/event/<uuid>` link. The full slug→uuid map from the 2026-08-03 run is saved at `scripts/ironman-site-event-uuids.json` — read this FIRST in future runs instead of reconstructing from the batch files.
- **Partial swim-cancellation (harder case than the full-cancellation precedent):** IRONMAN 70.3 Boise 2026 had swim cancelled for AG athletes only (wind/chop) while PRO did a modified swim minutes later — a genuine 2-wave subevent split in the labs-v2 data (separate subevent_uuid per wave, zero contactid overlap, fetched+merged manually). Modeled the same way as full cancellation regardless (drop the swim segment repo-wide for the category, note in description that PRO retains swim splits in the raw TSV column that just isn't mapped) rather than splitting into two categories — keeps one TSV per edition, consistent with how every other IRONMAN edition in this repo is structured.
- **JTU relay/leg filtering by column, not by program:** numadu 2026 (event_id 417) merged an individual race and a 3-person relay leg into ONE program/result_table (417_1) with 322 rows, distinguished only by a `部門名` column (エイジ vs 駅伝1区) — the usual "exclude by program_name" filter doesn't catch this since it's one program. **2026-09-07 run learnings** (last import run 2026-08-31, whose batch was still staged and uncommitted; covered a 7-day gap):
- **This playbook moved into the repository on this run**, because the user reported the import could not be run on another host: `.claude/commands/import-race.md` was already committed, but everything that made it *work* — this discovery file and the source-specific references beside it — lived only in a host-local memory directory keyed by the checkout path. - **JTU API response shapes — exact, because guessing them cost a wasted scan pass.** All three endpoints wrap their payload in `res.body`:
  - `/api/events/search?cond%5Bevent_id%5D=NNN` → `res.body.events[0]` (`event_name`, `event_date`, `event_location`, `event_result_opened`) and `res.body.programs["NNN"][]` (`program_id`, `program_name`).
  - `/api/programs/<pid>/result_tables` → `res.body` is a **bare array** of tables (no `result_tables` key); take `[0].result_table_id`.
  - `/api/results?cond%5Bresult_table_id%5D=NNNN` → `res.body.result_cols[]` (caption in `result_col_caption`, order in `result_col_order`) and `res.body.result_list[]` (**`result_list`**, not `results`; cells are `col_1`..`col_N` positional, `null` = empty).
  A wrong key guess yields a silent zero-row / zero-event result, which looks exactly like "nothing new" — always assert a nonzero count on a range you know is populated before trusting a sweep.

- **IRONMAN:** the sitemap-derived `scripts/ironman-site-event-uuids.json` (169 events) scanned cleanly with 0 errors over a 2026-08-01..09-07 window. Found **IRONMAN 70.3 Baku (2026-09-05) — a genuinely new event**, inaugural: its canonical labs-v2 event page lists exactly one subevent. Verified against race-info.json by name and by `azerbaijan|baku|caspian` token search (0 hits) before creating the event, per the duplicate-event rule above. The redirect gotcha appeared again (the subevent uuid returns a ~50-byte body containing the canonical event path).
- **`pro=0` is not by itself a partial-upload signal.** im703_knokke_heist 2026 returned 0 PRO rows where 2025 had 46, but its age-group field was *larger* than 2025 (2260 vs 1954 across 21 age groups) — a race simply not hosting a pro field that year. The PRO-only gotcha is the opposite shape: pro count ≈ total row count.
- **Source-side missing splits, baselined:** im703_baku 2026 has 19 finishers with a blank Bike or Run split but a valid total, and fujikawaguchiko 2026 has 3 finishers with blank bike+run laps but a valid 総合記録 — verified in the raw source rows, so recorded via `check-integrity.js --update` rather than treated as an import defect.

- **JMA publishes the 天気 (weather symbol) column late — a freshly imported domestic race gets an all-`UNKNOWN` weather file if you don't handle it.** Found only by an aggregate scan (`weatherCode` distribution across all 2,227 weather files): all three JP editions imported this run were 100% UNKNOWN, while the 2025 file used to validate the generator was fine. The 天気 cell is simply empty on `hourly_s1` for recent dates, and some automated stations (相川) never report it at all. `scripts/gen-weather-jma.py` now fills **only the empty condition cells** from Open-Meteo's WMO code for the same hour and coordinates (`--no-fill-weather` opts out); every measured quantity still comes from JMA, and a date where JMA does have 天気 is left untouched (verified: the 河口湖 2025 output is byte-identical before and after the change). Cross-checked the filled codes against JMA's own 降水量 column — 伊良湖 25mm from 12h, 河口湖 73mm from 9h, 相川 0mm all day — and the filled RAIN/CLEAR pattern matches in all three.
- **Never judge a generated weather file by one edition.** The single-file spot check that validated the generator looked perfect; the defect was visible only in the corpus-wide `weatherCode` histogram. Same lesson as the aggregate-audit rule for TSVs.
- **`master/2025/irago/weather-data.json` was broken and is now regenerated** (it recorded an impossible sunset of 19:28 for 2025-09-14 at 34.6°N — the true value is 18:02 — and temperatures matching no JMA station). Regenerated from 伊良湖 51/47653. **A spot check of `master/2024/irago/weather-data.json` shows the same signature** (stored 3am 27.3°C/70% vs JMA 25.8°C/91%, sunset 18:06 vs 18:11), so the irago series is very likely mis-sourced for 2019/2022/2023/2024 as well — regenerating them is a pending user decision, not done here.
- Sado station question resolved by measurement rather than preference: 相川 (54/47602) is ~6 km from the 佐和田 swim start, so it is used for 2026; `master/2025/sado/weather-data.json` came from 新潟 (54/47604), 60 km away on the mainland. Open-Meteo ERA5 at the exact venue coordinates was fetched as an independent cross-check and agrees with 相川 to ~1–2°C, which is what settled it — the remaining 相川 gap was the missing 天気 column, now filled from that same source rather than by switching the whole file to a model reanalysis (which would have thrown away real visibility and station observations).
- Repo-wide daylight-length scans need latitude awareness: a naive "8h–16h daylight" filter flags ~150 legitimate high-latitude European summer editions (Frankfurt, Elsinore, Jönköping, Haugesund, Finland). Useless as written; only the physically impossible cases (a Japanese September sunset at 19:28) are worth chasing.
